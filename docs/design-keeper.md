# Design: the keeper (go-gate step 2), draft for review

Status: draft 2, 08/10/2026, after the council review (FIX FIRST, 4/4). Implemented in keeper/ (not installed yet).

## Why

Two external audits of v0.8 and v0.9 showed the same class of weakness: go-gate runs with the agent's rights and reads
the text the agent writes. An agent that wants to can write the approval state, replay or forge a GO, or remove the hook.
Better patterns raise the cost; they do not change the class. The fix is to move the approval out of the agent's reach.

## Goal for v1 (minimal)

An action that changes something runs only if a human approved a plan that covers it, and **the agent cannot create,
change or forge that approval**, even if it tries. Output filtering (secret-guard) stays in the agent's process for v1.

## Threat model

- In scope: an agent that is careless, or that deliberately tries to act without approval (writes files, edits its own
  hooks, crafts messages, replays an old GO).
- Out of scope: an agent with root/admin rights on the machine where the keeper runs; a compromised human phone or
  Telegram account; side channels.
- Precondition, stated in the README: **the agent must not be root/admin where the keeper runs.** On the Mac, Claude
  Code runs as an ordinary user who can `sudo` only with a password the agent does not have. On a server where the
  agent runs as root (e.g. a container), the keeper cannot protect anything until the agent runs as a normal user.

## Components

1. **keeperd**: a small daemon (Python, stdlib only) running as a dedicated system user `_keeper` (macOS LaunchDaemon /
   systemd unit). Owns its state in `/var/lib/keeper/` (mode 700, `_keeper`). Listens on a Unix socket
   `/opt/agent-guardrails/run/keeper.sock` on macOS, `/run/keeper/keeper.sock` on Linux (group-readable by the agent's user, so the hook can talk to it; nothing else).
2. **An approval channel the agent does not control**: a second, dedicated Telegram bot ("keeper bot"). Its token is
   readable only by `_keeper`. The agent's own Telegram plugin cannot read its updates, and Telegram lets only one
   poller per bot, so the agent cannot read or answer its messages either.
3. **The go-gate hook becomes a thin client**: it forwards the raw tool call (tool name and input, as Claude Code passes
   it) to keeperd and applies the answer. **keeperd does the classification**, so a hook that lied about it would gain
   nothing (council review: the first draft trusted a classification sent by the agent's side).
4. **The hook's code is root-owned**: installed in `/opt/agent-guardrails/lib/` (root, 755; the installer checks that no parent directory is writable by the agent), run as
   `/usr/bin/python3 -I` (isolated mode: no user site-packages, no PYTHONPATH), so the agent's user cannot edit the
   code, the interpreter or its modules.
5. **Claude Code managed settings** (`/Library/Application Support/ClaudeCode/managed-settings.json` on macOS,
   root-owned): register the hook so the agent's user cannot remove or override it, and deny `Bash`/`Write`/`Edit` on the
   keeper's and the guardrails' paths.

## Flow

1. The agent proposes a plan by running `keeper-propose --scope … --text …`. keeperd answers that command itself in
   the hook's check (so it knows the real session id) and never lets it run. It carries `{text, scope:{id, targets,
   actions, ttl}}` to keeperd over the socket.
2. keeperd stores it as pending, computes `plan_hash = sha256(text + scope)`, and sends it to the human through the
   keeper bot, with two inline buttons: **Approve** and **Reject**. The message's first lines are **generated by keeperd
   from the structured scope** (targets, actions, TTL), so prose cannot hide a wide scope; the agent's explanation comes
   after, labelled as such. At most 3 pending proposals per hour (no flooding).
3. The human taps **Approve**. keeperd receives the callback from Telegram itself and checks: sender = the configured
   owner id; the callback refers to the pending plan's hash; the plan is less than 2 h old; the callback was not used
   before. Then the plan becomes active for its TTL (default 1 h, max 4 h).
4. On every PreToolUse, the hook sends `{session, tool, input}` to keeperd. keeperd classifies, checks the active plan
   of that session (every object in scope, as in v0.9.1), answers allow / deny with a reason, and logs it.
5. The socket is owned by `_keeper`, group `keeperclients` (the agent's user), mode 660;
   keeperd reads the peer's uid (`getpeereid`) and only answers the configured agent user.
6. Revocation: the **Stop** button on any approval message ends every active plan, in every session, at once. It does not stop a process already started; that is stated in the message.

## What changes for the attacks seen in the audits

| Audit finding | With the keeper |
|---|---|
| Writing the gate's state file (symlink, `$F`, …) | The state belongs to `_keeper`; the agent's user cannot write it. |
| A forged or replayed `GO` (channel header, old message_id) | A GO is a button press on the keeper bot, delivered by Telegram to keeperd, bound to the plan hash, single use. Text in the agent's conversation never approves anything. |
| A plan approved before it was delivered | keeperd sends the plan itself; the human approves what they saw. |
| Removing or editing the hook | Managed settings (root-owned) register it; the agent's user cannot change them. |
| Bypassing the classifier (Python, opaque commands) | The classifier runs in keeperd (root-owned code), not in a hook the agent could edit. Running a program from a scratch path or changing PATH is opaque. A read command that an option or a config file makes execute or write is opaque too (ssh ProxyCommand/-F, awk -f, sed -e w, curl -K, git read verbs outside a declared safe repo, a PAGER/LESSOPEN/GIT_* prefix; see Known limits). Opaque commands need `actions=script` in an approved plan. The heuristic classifier is still the weak point, now much narrower and bounded by what the human approved. |

## Known limits (be precise about what is proven)

The keeper gives two different guarantees, and only the first is strong:

1. **The approval cannot be forged by the agent.** The state is `_keeper`'s, the approval is a button press on a bot
   only `_keeper` can read, bound to the plan hash and single use, and the hook is root-owned in managed settings.
   An agent with the user's rights (not root) cannot create, change or replay it. This is the design's real contribution.
2. **The gate decides what counts as a change** with a heuristic classifier. It is not a proof. The 08/10 review found a
   whole class it mislabelled as reads (commands that execute or write through an option or a config file); those are
   fixed (K1-K9) and tested, but the classifier stays heuristic, so treat any new "read" that can run a program as a
   bug to report, not as a guarantee.

Still open, and stated so a reader does not over-trust the gate:

- **`actions=script` / opaque is unbounded by design.** A command approved as `script` can do anything the agent's user
  can. The real limit there is what the human approves, and least privilege underneath.
- **git in an agent-writable repo.** A git read verb is a read only in a repo listed in `safe_git_repos` (empty by
  default; set with `install-keeper.sh --safe-git-repo`). Elsewhere it is opaque, because a repo-local config can run a
  program. If a declared safe repo is itself writable by the agent, that protection is void.
- **TOCTOU on files.** `python3 script.py` is judged on the file keeperd reads; the file can change before it runs.
- **A process started under an approved plan keeps running after the plan ends.** The keeper gates tool calls, not
  the processes they spawn.
- **Output filtering (secret-guard) still runs in the agent's process** for v1.

The design that would actually bound the `script` class is an isolated executor under another user; it is the v2
direction, not done here.

## Failure modes

- keeperd down or socket missing: the hook denies changes (fail closed), reads still pass. The human gets a keeper-bot
  message on daemon start/stop.
- Telegram down: no new approvals; active plans keep running until their TTL.
- One keeperd and one keeper bot per machine. The server is out of scope for v1 until its agent runs as a normal
  user (root in the container could become `_keeper`).

## What the keeper does not do (stated in the README)

- It gates **tool calls**. A command approved as `script` can do anything the agent's user can do; a background process
  started under an approved plan keeps running after the plan ends. The real limit is what the human approves.
- The classifier is still heuristic; opaque commands always need an explicit `script` action.
- A design where every change runs in an isolated executor under another user (council isolated alert) is stronger and is
  noted as the direction for v2.

## Not in v1

- Output filtering in a separate process (secret-guard stays a hook).
- Multi-user approvals, a web UI.

## Testing

- Unit tests for keeperd (state machine, hash binding, single use, TTL, owner check), with a fake Telegram.
- An adversarial test as the agent's user: try to write the state, call the socket with a fake approval, replay a
  callback, edit the managed settings, kill the daemon. Each must fail, and the failure must be logged.
- A week in block mode on the Mac before v1.0.

## Open questions for the review

1. Is a second Telegram bot the right approval channel, or should the approval come through something else the agent
   cannot read (e.g. a passkey-protected web page served by keeperd)?
2. Is the classification still in the hook acceptable for v1, given the hook runs as the agent?
3. Is "the agent must not be root" a clear enough precondition, and should the server setup move to a non-root agent
   before v1?

# Design: the keeper (go-gate step 2), draft for review

Status: draft 2, 08/10/2026, after the council review (FIX FIRST, 4/4). Implemented in keeper/ (not installed yet).

## Why

Two external audits of v0.8 and v0.9 showed the same class of weakness: go-gate runs with the agent's rights and reads
the text the agent writes. An agent that wants to can write the approval state, replay or forge a GO, or remove the hook.
Better patterns raise the cost; they do not change the class. The fix is to move the approval out of the agent's reach.

## Goal for v1 (minimal)

An action that changes something runs only if a human approved a plan that covers it, and **the agent cannot create,
change or forge that approval**, even if it tries. Output filtering (secret-guard) stays in the agent's process for v1.

## Threat model

- In scope: an agent that is careless, or that deliberately tries to act without approval (writes files, edits its own
  hooks, crafts messages, replays an old GO), or that tries to **read the keeper's log and state**, or to make the
  keeper print them (a socket op, a command, a message to the bot).
- Out of scope: an agent with root/admin rights on the machine where the keeper runs; a compromised human phone or
  Telegram account; side channels.
- Precondition, stated in the README: **the agent must not be root/admin where the keeper runs.** On the Mac, Claude
  Code runs as an ordinary user who can `sudo` only with a password the agent does not have. On a server where the
  agent runs as root (e.g. a container), the keeper cannot protect anything until the agent runs as a normal user.

## Components

1. **keeperd**: a small daemon (Python, stdlib only) running as a dedicated system user `_keeper` (macOS LaunchDaemon /
   systemd unit). Owns its state in `/var/lib/keeper/` (mode 700, `_keeper`). Listens on a Unix socket
   `/opt/agent-guardrails/run/keeper.sock` on macOS, `/run/keeper/keeper.sock` on Linux (group-readable by the agent's user, so the hook can talk to it; nothing else).
2. **An approval channel the agent does not control**: a second, dedicated Telegram bot ("keeper bot"). Its token is
   readable only by `_keeper`. The agent's own Telegram plugin cannot read its updates, and Telegram lets only one
   poller per bot, so the agent cannot read or answer its messages either.
3. **The go-gate hook becomes a thin client**: it forwards the raw tool call (tool name and input, as Claude Code passes
   it) to keeperd and applies the answer. **keeperd does the classification**, so a hook that lied about it would gain
   nothing (council review: the first draft trusted a classification sent by the agent's side).
4. **The hook's code is root-owned**: installed in `/opt/agent-guardrails/lib/` (root, 755; the installer checks that no parent directory is writable by the agent), run as
   `/usr/bin/python3 -I` (isolated mode: no user site-packages, no PYTHONPATH), so the agent's user cannot edit the
   code, the interpreter or its modules.
5. **Claude Code managed settings** (`/Library/Application Support/ClaudeCode/managed-settings.json` on macOS,
   root-owned): register the hook so the agent's user cannot remove or override it, and deny `Bash`/`Write`/`Edit` on the
   keeper's and the guardrails' paths.

## Flow

1. The agent proposes a plan by running `keeper-propose --scope … --text …`. keeperd answers that command itself in
   the hook's check (so it knows the real session id) and never lets it run. It carries `{text, scope:{id, targets,
   actions, ttl}}` to keeperd over the socket.
2. keeperd stores it as pending, computes `plan_hash = sha256(text + scope)`, and sends it to the human through the
   keeper bot, with two inline buttons: **Approve** and **Reject**. The message's first lines are **generated by keeperd
   from the structured scope** (targets, actions, TTL), so prose cannot hide a wide scope; the agent's explanation comes
   after, labelled as such. At most 3 pending proposals per hour (no flooding).
3. The human taps **Approve**. keeperd receives the callback from Telegram itself and checks: sender = the configured
   owner id; the callback refers to the pending plan's hash; the plan is less than 2 h old; the callback was not used
   before. Then the plan becomes active for its TTL (default 1 h, max 4 h).
4. On every PreToolUse, the hook sends `{session, tool, input}` to keeperd. keeperd classifies, checks the active plan
   of that session (every object in scope, as in v0.9.1), answers allow / deny with a reason, and logs it.
4a. `keeper-propose --wait SECONDS` (v1.0): after keeperd records the proposal exactly as in step 1-2, the hook
   polls a new, read-only socket op, `status`, by the plan's fingerprint only (never its text or scope), until a
   human decision lands or `wait_max_sec` (50 s by default, see 4b) passes. Still one Bash tool call, still denied (there is
   nothing to run), still the same socket -- no new channel, no change to what counts as approved. `status`'s own
   vocabulary is deliberately closed to four words (pending/approved/rejected/expired); a plan keeperd never saw is
   reported "expired" too, so a socket client (bounded to the configured agent uid regardless) cannot use a fifth,
   distinguishable "unknown" to probe for live fingerprints. The decision itself is still written only by `decide()`
   (step 3), from a button press on the keeper bot; `status` only reads what `decide()` already wrote, so a hook
   that waits can shorten how long the agent takes to notice a decision, never change what the decision was. The
   wait does not hold keeperd's approval lock: each poll takes it only for the instant it reads the state, so a
   session waiting on its own proposal never blocks a button press, another session's check, or `/status`/`/stop`.
4b. Hook timeout (the fail-open risk of `--wait`). The wait runs inside the hook process, and Claude Code kills a
   command hook at its `timeout`. Per the Claude Code hooks documentation, a PreToolUse command hook that times out
   "doesn't block the tool call" (it continues through the normal permission flow; `onFailure: "block"`, in recent
   versions, changes that), and the default command timeout is 600 s. A wait longer than the timeout would thus end
   not in a deny but in a hook that is simply gone, which for a gate is the wrong failure mode (for a
   `keeper-propose` call the fall-through is harmless, since the command only prints "not installed", but the same
   hook serves every other tool call, so the rule is kept absolute). Hence: the installer writes an explicit
   `timeout` (60 s) in the hook entry; `wait_max_sec` defaults to 50 s; the rule is `hook_timeout_sec >= wait_max_sec
   + 10` (one in-flight 5 s status poll, the 2 s poll interval, start-up); the installer refuses a combination that
   breaks it and keeperd clamps every `--wait` to `hook_timeout_sec - 10`. A longer wait is an operator choice that
   needs both numbers raised together. What the harness really does when a hook is killed mid-sleep is documented but
   has not been observed on a real session (see PR #16 for the test to run).
5. The socket is owned by `_keeper`, group `keeperclients` (the agent's user), mode 660;
   keeperd reads the peer's uid (`getpeereid`) and only answers the configured agent user.
6. Revocation: the **Stop** button on any approval message ends every active plan, in every session, at once. It does not stop a process already started; that is stated in the message. `/stop <id>` (12/10's text commands) ends only the one plan.

## Several active plans at once (20/10)

**The problem a single `s["active"]` caused in real use.** Before this, a session held at most one active plan:
approving a new one **replaced** whatever was running. When the owner approved a small, 30-minute card while a
broad, 300-minute one from a parallel sub-agent was still in flight, the broad plan vanished and everything that
depended on it was refused mid-task ("the approved plan X does not cover this action") — including work that had
nothing to do with the small card just approved. Observed in production on 20/10/2026. The fix: `active` becomes a
list, bounded by `max_active_plans` (default 3, hard cap 5 — enforced in `Keeper.__init__`, so a tampered or
careless config file cannot raise it past 5).

**The coverage rule: one plan covers an action, whole, or it is refused — never two plans together.** An action is
allowed when at least one active plan covers it completely, exactly as `go_gate.covers()` already decided for a
single plan (every object of a multi-object verb matched against that plan's own targets, `script` required for
an opaque command, and so on — none of that changed). The only thing that changed is *which* plan `check()` asks:
instead of the one-and-only `active`, it tries every active plan in turn and accepts the first that says yes.

This deliberately does **not** let two plans add up: if plan A has `actions=deploy, targets=web` and plan B has
`actions=edit, targets=app`, neither covers `docker restart app` (A: wrong target; B: wrong category) even though
the category is approved by A-or-B's category set and the target by B's targets — accepting that would mean a
"union" of coverage across plans, which is exactly the kind of implicit widening the keeper exists to prevent (a
scope the owner never saw and never approved in that combination). The one case where two plans legitimately split
one tool call is a **compound Bash command go-gate already splits into stages** (`docker restart web && docker
restart db`): each stage is still matched against a single plan, in full — stage 1 might be covered by plan A and
stage 2 by plan B, but neither stage is ever covered by half of each. This is not new coverage logic; it already
existed for a single active plan (`self.gate.CHANGES`, one tuple per stage) and continues unchanged, just checked
per stage against every active plan instead of only one.

**The cap: reached, never silently.** Approving a plan that would push the session over `max_active_plans` drops
the **oldest** active plan (by approval time; the one just approved is never a candidate, by construction — see
`Keeper._activate`). Both sides are told: the approval card shows, before the tap, what approving it will do
("adds to: …", "renews: …", or the cap warning naming which plan would be dropped); the owner's confirmation names
the dropped plan; `/plans` and the log carry a `plan-evicted` event; and the agent can always see which plans are
currently active, in `keeper-status`'s own answer and in the reason of any later refusal (`"no active plan (ids…)
covers it"`). There is no channel that tells the agent synchronously the instant an eviction happens — keeperd has
no way to push to an agent that is not, at that moment, making a tool call — so the agent learns of it the same way
it learns of expiry: the next denied call, or its own `keeper-status`.

**Renewal.** A newly-approved plan whose `id` matches one already active replaces that one *in its slot* (fresh
hash, fresh expiry) instead of adding a second entry; it never counts against the cap and never evicts anything.
This lets an agent legitimately extend a plan it is still using without burning a slot on itself.

**Compatibility.** `migrate_state()` runs on every load and turns an old `state.json`'s single `active` dict into a
one-element list, same plan, same hash, same expiry — nothing is widened, nothing is dropped. A state already in
the list form, or with no `active` key, passes through unchanged.

**Why pending proposals stay one-at-a-time per session.** Only `active` (approved) plans needed to become a list.
A session can still have only one *pending* (not yet approved) proposal: a second `keeper-propose` while one is
pending overwrites it, exactly as before this change — the owner would otherwise have to track which of several
pending cards a given button press belongs to, which the fingerprint-and-nonce binding already makes awkward by
design (council review, 08/10: "an old button after a new proposal must not approve it").

## What changes for the attacks seen in the audits

| Audit finding | With the keeper |
|---|---|
| Writing the gate's state file (symlink, `$F`, …) | The state belongs to `_keeper`; the agent's user cannot write it. |
| A forged or replayed `GO` (channel header, old message_id) | A GO is a button press on the keeper bot, delivered by Telegram to keeperd, bound to the plan hash, single use. Text in the agent's conversation never approves anything. |
| A plan approved before it was delivered | keeperd sends the plan itself; the human approves what they saw. |
| Removing or editing the hook | Managed settings (root-owned) register it; the agent's user cannot change them. |
| Bypassing the classifier (Python, opaque commands) | The classifier runs in keeperd (root-owned code), not in a hook the agent could edit. Running a program from a scratch path or changing PATH is opaque. A read command that an option or a config file makes execute or write is opaque too (ssh ProxyCommand/-F, awk -f, sed -e w, curl -K, git read verbs outside a declared safe repo, a PAGER/LESSOPEN/GIT_* prefix; see Known limits). Opaque commands need `actions=script` in an approved plan. The heuristic classifier is still the weak point, now much narrower and bounded by what the human approved. |

## Known limits (be precise about what is proven)

The keeper gives two different guarantees, and only the first is strong:

1. **The approval cannot be forged by the agent.** The state is `_keeper`'s, the approval is a button press on a bot
   only `_keeper` can read, bound to the plan hash and single use, and the hook is root-owned in managed settings.
   An agent with the user's rights (not root) cannot create, change or replay it. This is the design's real contribution.
2. **The gate decides what counts as a change** with a heuristic classifier. It is not a proof. The 08/10 review found a
   whole class it mislabelled as reads (commands that execute or write through an option or a config file); those are
   fixed (K1-K9) and tested, but the classifier stays heuristic, so treat any new "read" that can run a program as a
   bug to report, not as a guarantee.

Still open, and stated so a reader does not over-trust the gate:

- **`actions=script` / opaque is unbounded by design.** A command approved as `script` can do anything the agent's user
  can. The real limit there is what the human approves, and least privilege underneath.
- **git in an agent-writable repo.** A git read verb is a read only in a repo listed in `safe_git_repos` (empty by
  default; set with `install-keeper.sh --safe-git-repo`). Elsewhere it is opaque, because a repo-local config can run a
  program. Two refinements (R4, 09/10): a `cd`/`pushd` into another directory before the git command is followed, so
  `cd /tmp/x && git status` is judged against `/tmp/x`, not the session cwd; and a nested repo (`<safe>/sub/.git`) does
  not inherit the parent's trust. Still void if a declared safe repo is itself writable by the agent: then the agent can
  arm `core.fsmonitor` in its `.git/config`. To reduce that, writing a repo's git-exec surface (`.git/config`, a hook,
  `.gitattributes`, `.gitmodules`, or `git config` of an exec key such as `core.fsmonitor`/`core.pager`/`alias.*`) now
  needs `actions=script`, not `edit`. The nested-repo check reads the filesystem, which keeperd (running as `_keeper`)
  may not be able to traverse in the agent's tree; there it is best-effort and falls back to the prefix rule. The strong
  parade, for later: the installer makes each safe repo's `.git/config` root-owned.
- **A symlink inside a safe repo can point at a different repo (council of 11/10, owner-checked).** The agent's home
  is normally mode 750, and `_keeper` has no group membership there, so it cannot traverse into it. `os.path.realpath`
  then cannot follow (or even stat) a symlink inside a declared safe repo that points outside it, and
  `_nested_git_between` skips what it cannot stat (same best-effort fallback as above). The symlink's target is then
  judged AS the safe repo: a git read verb run through it is a read, with none of the target's own `.git/config` or
  hooks checked. This is accepted, not fixed, for v1 (see the owner's decision below), for two reasons:
  - **it needs a prior write to exist.** The agent cannot plant the symlink, or clone the hostile repo it points at,
    without that write itself going through go-gate: in block mode it needs a plan whose actions cover it (`edit` at
    least; see the `~/bin` / `script` carve-out above for the same reasoning applied to planted executables). A
    careless `edit` plan scoped broadly inside the safe repo's tree is the realistic way this gets created, not a
    cold read-only bypass with no prior approval at all.
  - **the installer cannot grant the traversal without widening `_keeper`'s reach past this repo.** An ACL giving
    `_keeper` search-only access to the agent's home (so it could resolve the symlink) would need to be scoped
    per-repo to stay narrow, applied only with `--apply`, and reversed by the rollback; that is real installer work,
    better done once, deliberately, than as a last-minute item here. `go-gate/test_disguise.py` documents the
    resulting behaviour (a symlink the check cannot stat is treated as inside the safe repo) rather than asserting
    it should be a change, since asserting that would require the fix this limit explicitly defers.
  Until it is fixed: do not declare `--safe-git-repo` on a tree where the agent can create symlinks and you have not
  reviewed what they point at, and read any plan that writes inside a safe repo before approving it: creating the
  symlink there is the step that opens this gap.
- **TOCTOU on files.** `python3 script.py` is judged on the file keeperd reads; the file can change before it runs.
- **A process started under an approved plan keeps running after the plan ends.** The keeper gates tool calls, not
  the processes they spawn.
- **Output filtering (secret-guard) still runs in the agent's process** for v1.

The design that would actually bound the `script` class is an isolated executor under another user; it is the v2
direction, not done here.

## Future option: neutralise git config by rewriting the command (studied, not implemented)

Claude Code's PreToolUse hook can rewrite a tool call before it runs, via `updatedInput` under `hookSpecificOutput`
(https://code.claude.com/docs/en/hooks, *PreToolUse decision control*). Instead of refusing a git read outside a safe
repo, keeperd could prepend hardening so a repo-local config cannot run a program, and then allow it. This was studied
and deliberately left out of this PR.

**The config keys git executes** (current git; corroborated across the git docs and several hardening projects):
`alias.*` when the value starts with `!`; `core.pager`, `pager.<cmd>`, `core.editor`, `sequence.editor`,
`core.askPass`, `core.fsmonitor`, `core.sshCommand`, `core.gitProxy`, `core.hooksPath`; `credential.helper` and other
`credential.*` helpers; `diff.external`, `diff.<driver>.command`, `diff.<driver>.textconv`, `difftool.<t>.cmd`;
`filter.<driver>.clean` / `smudge` / `process`; `merge.<driver>.driver`; `gpg.program`, `gpg.<fmt>.program`;
`init.templateDir` (installs hooks); `uploadpack.*` / `receive.*` (server side). `include.path` / `includeIf.*` pull in
another config file that can set any of the above. The same values also arrive through `-c key=val`, `--config-env`,
and the `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_*`/`GIT_CONFIG_VALUE_*` and `GIT_*` environment variables.

**Why `-c key=` is not enough.** `git -c core.fsmonitor= …` clears one fixed key. But `alias.*`, `filter.*`,
`diff.*.command` and `credential.*` are *pattern* namespaces: you cannot enumerate every `alias.<name>` the repo config
defines, and `-c` cannot wildcard. A repo could define `alias.st = !evil` and the agent run `git st`. So a complete
rewrite would need to clear every known key *and* forbid any alias/unknown subcommand, which is brittle.

**The environment alternative.** `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1` drops the user's and system config,
and `GIT_CONFIG_SYSTEM=/dev/null` likewise, but none of these drop the *repo-local* `.git/config`, which is exactly the
file the agent controls. `safe.directory` only governs whether git trusts the directory's ownership; it does not stop a
trusted repo's local config from running a program. So the environment route does not close the hole either.

**Recommendation.** Do not rely on rewriting for v1: the key set is open-ended and a miss silently re-opens code
execution. Keep the current rule (a git read is a read only in a declared safe repo, no nested repo, config surface
needs `script`), and make the real fix ownership: the installer chowns each safe repo's `.git/config` (and
`.git/hooks`) to root, so the agent cannot arm an exec key in the one place the environment and `-c` cannot cover.
Revisit rewriting only as defence in depth once that is in place.

## The log summary: why it goes to Telegram only

Before block mode the owner must read what would have been refused, and that is in the keeper's log, which only `_keeper`
reads. Two exits exist, both for the human: `/summary` on the keeper bot, and `sudo keeper-summary` for root. **No socket
op returns any of it.** The socket is the agent's door: anything it can ask for, a compromised agent can ask for, and the
log shows which commands the keeper let through and why, which is a map of the gate. So the summary is not an op, and a
Bash call such as `keeper-summary` gets a decision and a reason like any other call.

The summary is built so that it is safe even if it is read by someone it was not meant for:

1. **The log does not hold the arguments of a refused call.** It is logged as a *shape*: its first word, the subcommand for a
   short list of known CLIs (git, docker, kubectl, systemctl…), and its category, arguments replaced by `…`
   (`docker restart … [deploy]`). The subcommand is kept only when it is a plain lowercase word that the mask leaves
   untouched; anything else (a path, a value) ends the shape. A secret typed in a command therefore never reaches the log, let alone
   Telegram. (Other fields exist, such as plan and session ids; the summary prints none of them.)
2. **Only validated values are printed.** The tool name arrives on the socket, so it is agent-controlled text. Tool names,
   categories and shapes are printed only if they match a strict format; anything else is counted as `<other>` or "no
   recorded shape". An agent cannot put a sentence in front of the owner through the summary.
3. **The whole text is masked** (patterns from secret-guard) before it is sent, as a last layer, and cut below the
   Telegram limit.

Only the owner, in the configured chat, is answered (the same test as for the approval buttons). The summary is computed
without the approval lock, so reading a big log cannot make the hook wait. The log is append-only and never rotated; the
summary reads at most its last 32 MiB.

Residual risk: the keeper's own Telegram channel. Whoever reads the owner's chat reads the summary, which shows counts and
shapes, not arguments. That is the same exposure as the approval cards.

## Failure modes

- keeperd down or socket missing: the hook denies changes (fail closed), reads still pass. The human gets a keeper-bot
  message on daemon start/stop.
- Telegram down: no new approvals; active plans keep running until their TTL.
- One keeperd and one keeper bot per machine. The server is out of scope for v1 until its agent runs as a normal
  user (root in the container could become `_keeper`).

## What the keeper does not do (stated in the README)

- It gates **tool calls**. A command approved as `script` can do anything the agent's user can do; a background process
  started under an approved plan keeps running after the plan ends. The real limit is what the human approves.
- The classifier is still heuristic; opaque commands always need an explicit `script` action.
- A design where every change runs in an isolated executor under another user (council isolated alert) is stronger and is
  noted as the direction for v2.

## Not in v1

- Output filtering in a separate process (secret-guard stays a hook).
- Multi-user approvals, a web UI.

## Testing

- Unit tests for keeperd (state machine, hash binding, single use, TTL, owner check), with a fake Telegram.
- An adversarial test as the agent's user: try to write the state, call the socket with a fake approval, replay a
  callback, edit the managed settings, kill the daemon. Each must fail, and the failure must be logged.
- `keeper-propose --wait` (v1.0): the `status` op's peer-uid gate and closed vocabulary, the ledger isolating two
  simultaneous plans, a late click still read as expired, pruning by age, and the end-to-end wait against a real
  socket and a real hook subprocess -- approved/rejected/expired while still waiting, the wait itself running out,
  a daemon that is down from the start or stops answering mid-wait; the explicit hook `timeout` written by the
  installer (idempotent, upgrades an old entry), the refusal of a `wait_max_sec` that does not fit under it, and
  keeperd's clamp. Each guard above is mutation-checked (the
  relevant line disabled or reordered in a scratch copy of keeperd.py): the test that exercises it fails.
- A week in block mode on the Mac before v1.0.

## Open questions for the review

1. Is a second Telegram bot the right approval channel, or should the approval come through something else the agent
   cannot read (e.g. a passkey-protected web page served by keeperd)?
2. Is the classification still in the hook acceptable for v1, given the hook runs as the agent?
3. Is "the agent must not be root" a clear enough precondition, and should the server setup move to a non-root agent
   before v1?
